# 15. Chat Ownership by the Inviter, with an ECDH-Derived Chat Key

Date: 2026-09-23

## Status

Accepted - implemented 2026-09-23. Amends ADR 0004 decision 4 and ADR 0013
decision 7. Implementation plan: `docs/plans/chat-ownership-by-inviter.md`.

## Context

Today the chat document is created by the **invitee**, as part of accepting a
contact request (`contactService.acceptContactRequest` in imagey-web,
`ContactService.acceptInvitation` on the server): the invitee generates a
random chat key, files the chat document under their own "chats" document,
ECDH-wraps the key for the inviter (`ContactExchange.sharedKey`), and the
inviter later re-wraps it under their own "chats" key, which the server files
under the chat document in the invitee's tree (`ContactService.confirmReceipt`,
ADR 0004 decision 4). The invitee therefore owns every chat.

That was forced by key availability, not chosen: only the invitee knows both
public main keys at the moment the chat must be keyed. The inviter cannot learn
the invitee's public key at invite time - the invitee may not be registered
yet, and a lookup would reveal who is registered, which
`ContactService.invite` deliberately hides (it never lets the inviter tell a
registered from an unregistered address).

We want the **initiator of the contact (the inviter) to own the chat**, for
two reasons:

- **Federation (ADR 0013).** The `ContactExchange` always lives on the
  inviter's home server (A), because that is where `invite` runs. With the
  invitee as owner, a federated chat lives on the invitee's server (B) - two
  homes, a cross-server `confirmReceipt`, and domain-qualified
  `ContactExchange.chatId` (ADR 0013 decision 7). With the inviter as owner,
  exchange and chat are always co-located.
- **Guests never own anything.** A foreign principal has no home tree on A
  (ADR 0013 decision 3). Making the inviter - always a local account on the
  server the invite was issued from - the owner means the party that is
  possibly a guest never has to create the chat.

Additional requirement: **the invitee must be able to write messages directly
after accepting**, without waiting for the inviter's client to come online.

Naively moving chat creation to the inviter costs one handshake leg (the
inviter can only key the chat for the invitee after learning their public key
from the acceptance, and the invitee then has to confirm), and the invitee
could only chat once the inviter's client had picked up the acceptance.

## Decision

### 1. The chat key is derived, not transported

Both parties derive the same chat key independently from their main key pairs
(P-256, `Main Key Pair` in ENCRYPTION.md):

```
chatKey = HKDF-SHA-256(
    ikm  = ECDH(ownPrivateMainKey, otherPublicMainKey),
    salt = <empty>,
    info = "imagey-chat-key" 0x00 chatId 0x00 inviterUserId 0x00 inviteeUserId)
  -> AES-GCM-256, extractable
```

The `info` parts are separated by a NUL byte, so ids of varying length (e.g.
domain-qualified ones, ADR 0013) cannot run into each other.

- The invitee can compute it at accept time (they know the inviter's public
  key from the `INVITED` exchange); the inviter at pick-up time (they learn the
  invitee's public key from the `ACCEPTED` exchange). No party ever sends the
  chat key, wrapped or otherwise.
- The HKDF step is required. The existing `deriveKey` in `CryptoService.ts`
  feeds ECDH straight into AES-GCM, which yields one key per *pair of
  accounts*; binding `chatId` and both `UserId`s in `info` makes the key
  specific to this chat.
- The derived key is only needed **once** per party: each party immediately
  wraps it under their own "chats" document key, exactly like today's
  self-issued chat key entries. From then on, opening a chat is symmetric
  unwrapping as before (ADR 0004 decision 4: "no ECDH is needed to open a
  chat"). A later rotation of a main key pair therefore does not affect
  existing chats.
- Security is equivalent to today: today the chat key sits in the exchange
  ECDH-wrapped under the same static-static ECDH secret, so anyone holding
  either private main key could recover it; the same holds for a derived key.
  Neither variant has forward secrecy.

### 2. The inviter chooses the `chatId` at invite time

`POST {inviter}/contact-requests` gains a mandatory `chatId`, generated by the
inviter's client and stored on the `INVITED` exchange. The server rejects it
(`409`) if a document with that id already exists in the inviter's tree
(`DocumentRepository.documentExists`). Only the id exists at this point - no
document - so an invitation that is declined or never accepted leaves nothing
to clean up.

The inviter, not the invitee, picks the id: decision 4 grants the invitee
provisional write access to `{inviter}/documents/{chatId}/messages`, and that
must never be steerable onto an existing document of the inviter.

### 3. Three-leg handshake, invitee is ready after leg 2

| Leg | Actor | Action | Status |
|---|---|---|---|
| 1 | Inviter | Sends own public main key, own public-profile id, and `chatId`. | `INVITED` |
| 2 | Invitee | Derives `chatKey`; wraps it under their own "chats" key; sends own public main key, own public-profile id and that wrapped key. Adds the contact (`owner` = inviter) to their own "chats" document and shares their public profile into the chat (keyed with `chatKey`). **Can write messages from now on.** | `ACCEPTED` |
| 3 | Inviter (poll) | Derives `chatKey`; creates the chat document under their own "chats" document (atomic add-to-folder, self-issued key entry), with both public-profile ids in the chat metadata; shares their own public profile into the chat; confirms receipt. The server files the invitee's wrapped key (from leg 2) under the chat document in the inviter's tree - this grants the invitee the regular `member` role. | `RECEIVED` |

`ContactExchange` keeps its shape: `chatId` is now set from `INVITED` on,
`publicKey`/`publicProfileId` keep their "sender of the latest transition"
semantics, and `sharedKey` changes meaning from "chat key ECDH-wrapped for the
inviter" to "chat key wrapped by the invitee under their own 'chats' key"
(opaque to the inviter and the server, filed verbatim as
`EncryptedSharedKey(invitee, kid = invitee, sharedKey)` in leg 3). The
`RECEIVED` update carries no key any more.

In leg 3 the server additionally requires that the chat document exists in the
inviter's tree before filing the key (`409` otherwise) - the key file write
itself (`DocumentRepository.create`) does not check that.

### 4. Provisional chat membership for messages only

Between legs 2 and 3 the chat document does not exist yet. The invitee's
messages are nevertheless written to their **final location**,
`/users/{inviter}/documents/{chatId}/messages`, already encrypted with the
final chat key - so nothing has to be moved, re-encrypted or re-sent in leg 3,
and the server-stamped `sender` stays the invitee.

To allow this, the `member` check gets one narrowly scoped fallback:

> For `POST`/`GET {owner}/documents/{chatId}/messages` only, a caller is a
> `member` if `{owner}`'s tree holds a `ContactExchange` with
> `status == ACCEPTED`, `inviter == owner`, `invitee == caller` and
> `chatId == {chatId}`.

- Still two roles (ADR 0004 decision 1); this is an additional way to satisfy
  `member`, not a new role, and it does not apply to any other document
  endpoint (metadata, keys, content, uploads).
- **Never cached.** `declineInvitation` persists `DENIED` from any status, so
  an `ACCEPTED` exchange can still be withdrawn; the provisional grant must be
  re-evaluated on every request. After leg 3 the regular key entry takes over
  and is cached as before.
- `MessageService.sendMessage` currently rejects a message for a chat whose
  document does not exist (the guard against a stray `messages` folder in the
  caller's own tree). It must accept the provisional case too - the guard's
  intent (no messages outside a real or agreed chat) is preserved because the
  exchange names exactly this `(inviter, chatId)`.
- No conflict with leg 3's document creation: `DocumentService.validate` 409s
  only if the chat's **metadata file** already exists
  (`DocumentRepository.documentExists` checks `metadataFile`), not merely
  something under the document's prefix; with the blob store abstraction
  (ADR 0012) there are no directories anyway.
- The `sendMessage` relaxation applies to the invitee only
  (`ContactService.isProvisionalChatMember`); the inviter's client only knows
  the chat once it has run leg 3, at which point the chat document exists.

### 5. The invitee's client knows the chat key before the chat exists

`contactService.loadChatKey` currently loads the chat document from the
owner's tree to obtain key and `publicProfiles`. Before leg 3 that document
does not exist. The invitee's `ContactEntry` therefore carries an optional
`pending` part - the derived chat key (inside the "chats" document, which is
encrypted with the "chats" key, so no extra wrapping is needed) and the
inviter's public-profile id - used as a fallback while the chat document is
missing (only on `401`/`403`/`404`; any other failure is reported as an
error). Once the chat document loads successfully, the client removes the
`pending` part from the "chats" document.

### 6. Federation (amends ADR 0013 decision 7)

- The `ContactExchange`, the chat document, and all messages live on the
  inviter's server. `confirmReceipt` stays one local operation - the
  two-step "RECEIVED on A, key filed on B as a guest" split disappears.
- `ContactExchange.chatId` needs **no** domain component: it always names a
  document in the inviter's tree on the exchange's own server. Only the
  client-side `ContactEntry.owner` (the invitee's chat list on B points to a
  chat on A) and the public-profile ids in the chat metadata (the invitee's
  lives on B) need domain qualification.
- A federated invitee performs legs 2 and all messaging as a guest on A,
  using only `member`-scoped calls (ADR 0013 decision 4). The provisional
  membership (decision 4) compares `UserId`s only, so it works unchanged for a
  `ForeignUserMapping` principal.
- The inviter needs a guest session on B only to read the invitee's public
  profile and images the invitee shares into the chat - unchanged.

## Consequences

- The inviter owns every chat; a guest never has to own one.
- The handshake stays at three legs, and **both** sides can write as early as
  possible: the invitee right after accepting, the inviter as soon as their
  client picks up the acceptance.
- No chat key is ever transported, not even wrapped; the exchange carries only
  an entry that is opaque to everyone but the invitee.
- One new, narrowly scoped authorization path (provisional membership for
  messages) that must be kept uncached and restricted to the messages
  sub-resource.
- The client gains an HKDF-based derivation and a `pending` fallback in the
  invitee's contact entry.
- Per ADR 0008 there is no production data migration: existing chats and
  in-flight exchanges are not carried over; test fixtures and Pact bodies are
  migrated in place.
